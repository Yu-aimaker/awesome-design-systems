# 敵対検証

実装者の説明を信じない。トークン表、DOM、実操作の3点で判定する。

対象が AwesomeDS 直分か、製品 DS 分かを最初に宣言する。製品 DS があるなら `DESIGN.md` と `AwesomeDS/` の両方に照らす。

## 1. トークン

- ページ地・本文・アクセント・danger が正本と一致するか
- 半径が 8/12 以外の場当たり値になっていないか
- 余白が 4 の倍数か
- 書体が Display / Sans / Mono の役割を守っているか

ずれは「意図した派生」か「漏れ」か。漏れは直す。派生は `DESIGN.md` に理由が無ければ不合格。

## 2. ブランド

- アクセントの意味が画面上で一貫しているか
- ロゴ・写真・イラストが部品より目立って操作を隠していないか
- コピーがブランド語彙と矛盾していないか（冗談の製品で官庁口調、など）

## 3. デザイン思考（人が困るか）

各主要フローで:

- 最初の操作は3秒以内に見つかるか
- 失敗したとき次の手が残っているか
- 空状態が「壊れている」ように見えないか
- スマホ幅でタップ対象が 40px を下回らないか

## 4. ブラウザキャプチャ（必須）

実ブラウザで次を撮り、判定をキャプチャに紐づける。スクリーンショット1枚の見た目確認は検証ではない。

| 項目 | 操作 | 合格 |
| --- | --- | --- |
| 主要フロー | 目的の完了までクリックする | 迷うラベル、死んだボタンが無い |
| フォーカス | Tab のみで往復 | リングが見える。順序がDOMと一致 |
| エラー | 空送信、ネットワーク失敗 | 文言が入力の近く、再試行がある |
| 縮小 | 390px 幅 | 横スクロール無し、行長が崩れない |
| Reduce Motion | OS 設定または CSS 強制 | ループと大きな移動が止まる |
| コントラスト | 本文と `inkSubtle` | 本文は十分、キャプションが本文代わりになっていない |

キャプチャには URL、幅、操作手順を残す。

## 5. レポート

```
不合格: <事実>
根拠: <AwesomeDS の節 or 製品 DESIGN.md>
直し: <具体的なトークン / コピー / 構造>
```

合格項目は短く列挙。褒めの抽象語は書かない。

## 禁止

- 「全体的に綺麗」で合格にすること
- 実装者に「意図は？」と聞いて納得して終えること（コードと画面で確認する）
- キャプチャ無しで Verifier 完了を宣言すること

## 合格（これ以外は後回し）

- キャプチャ表の全行に URL・幅・手順・合否がある
- 1行でも欠けたら未完了。見た目の一枚撮りは検証ではない
- 不合格は「事実 / 根拠の節 / 直し」の3行で書く
